# Explicit local Hunter sale workflow

`/shop/SellCard` now has an authenticated, persisted local implementation. It is enabled only by explicitly supplied profit rows; the default publishes `card_sell_profit:[]` and refuses sales with non-success code 2001. No original prices were recovered and no live sale or live profile change was performed.

Supply `BLUSTONE_CARD_SELL_PROFIT_JSON` with an array matching the recovered GetExtra grammar: `{rank,profit_type,profit_target,profit_qty}`. Alternatively, a disposable server fixture can use `new ServerState(baseUrl, filename, {hunterSaleProfits: rows})`. Type 2 credits gold; type 5 credits an item whose exact identity exists in the currently published item reference. Constructor options override the environment. Explicit malformed data fails construction; an explicit empty array disables selling. Rows are copied, validated and frozen once, so changing environment variables or a returned GetExtra object cannot silently change the server's settlement prices.

These quantities are supplied **local economic policy/data**, not recovered original prices. No shipped launch profile enables this option. A type-5 row must not invent a Chu-Coin identity from a screenshot or text label. Unknown reward identities refuse settlement.

The original parser and body evidence is recorded in [hunter-sale-and-growth-contract-2026-10-11.md](hunter-sale-and-growth-contract-2026-10-11.md): RequestSellCard Gf8df98 sends numeric `inst_id_list` serialized as one JSON form string; ParseSellCard Gf8ed98 consumes absolute `user.gold.cur` and additive `item[{inst_id,ref_id,added}]`, then removes its captured request vector only after success. No invented removed-list receipt is emitted. Sale rows select the **minimum published reference stat rank**, never the owned rank, birth rarity or GetLevel sell-price fixture.

The handler protects the leader, all saved decks, active ordinary/arena/search decks, locks and unresolved Mirage carry. Production uses the collision-free owned Hunter namespace and refuses low/reserved IDs; the pre-existing explicit legacy-ID fixture option is available only for historical tests. Unknown, duplicate or already removed sources refuse the entire request. A replay after a successful sale cannot credit again because those exact owned IDs no longer exist; no original native transaction nonce was recovered.

The planner validates ownership, every selected profit rank, item identities, inventory IDs/quantities, gold and allocation overflow before mutation. Selected removals, reward balances and the item allocator persist in one snapshot. A persistence failure restores the original roster arrays, wallet, item array and allocator before propagating the error. Card-book history, decks, progression, unaffected accounts and the monotone Hunter allocator are preserved. Sold starters are not replaced or granted again by this handler.

Validation: `npx tsx tests/hunter-sale.ts`, `npx tsx tests/hunter-sale-state.ts`, and `npm run build` pass. The state test uses authored gold17/item3 prices, disposable account files and real production Hunter IDs. It checks detached price publication, auth/cross-account ownership, rank selection, source replay, locks/commitments, reserved IDs, overflow, missing-row/unknown-item refusal, original book/allocator preservation, gold/item receipts, item-ID reuse and lock preservation, restart, and induced persistence failure with unchanged prior save bytes. Native sale UI and a complete original release economy remain unverified.

The full71-check suite and final build pass. Compiled encrypted disposable verification (`node scripts/verify-independent.mjs --fixture --profile current-e6-materials --exercise-sale`) publishes its authored gold13 profit row, refuses a protected main Hunter, sells exactly two seeded sources for gold26, rejects replay without another credit, and preserves the precise remaining game state after restart. One source has owned rank5 while its published reference minimum remains1. The fixture includes the matching previously-earned rank5 card-book entry before launch; sale neither creates nor removes that history. Unaffected fixture accounts stay exact. This CLI refuses preserved/private-state transaction exercises and cannot be combined with bulk promotion in the same run.
